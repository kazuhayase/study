## Problem Statement

A life insurance group with three entities (life insurance parent, IT subsidiary, DX
subsidiary) has talent and skills data scattered across departmental Excel files, an HR
system (Kaonavi), an external DX assessment tool (DIA by ExaWizards), and an online
learning platform (Udemy). The CIO — one of two VPs reporting directly to the CEO —
has ordered talent/skills visibility from multiple managers over multiple years. The
question "who in this org has skill X" cannot be answered today. Decisions about
hiring, training, and project staffing are made without data.

A prior attempt (HRMOS pilot at IT subsidiary) failed on two counts: manual file upload
friction killed adoption, and AI inference of skill levels from evaluation prose
over-reported capability. The answer is not less data engineering — it is more
disciplined data modeling with AI used only for parsing, not for scoring.

## Target User & Narrowest Wedge

**Primary user:** CIO/VP — wants a single view of skills, gaps, and talent across all
three entities. His benchmark is the DIA output for DX skills: a structured,
queryable picture of who has what at what level.

**Narrowest wedge:** IT entity skills heatmap — import the ITSS/DSS Excel

**Scale:** 500–2,000 employees across all three entities.

## Premises

1. Read-only analytics layer through September 2026. Write capability for IT/DX
   entities (goals, evaluations) is post-September scope.
2. Kaonavi is the employee master of record for life insurance. Employee identity
   for the insurance entity flows from Kaonavi.
3. The skill taxonomy has multiple sources requiring a unified mapping:
   ITSS + DSS (Excel/IPA), DX skills (DIA), learning signals (Udemy).
4. The Excel batch import to Snowflake is already working or nearly working.
   The schema wraps around it, not the other way.
5. AI is for data parsing and normalization only — splitting multi-value cells,
   extracting structured records from free-text job history entries, fixing
   malformed data in historical files. AI does not assess or modify
   explicit 1-5 skill level scores entered by humans.
6. Excel format standardization across entities is unknown. A data audit is
   the critical-path first task before schema finalization.
7. Incremental delivery: IT entity skills map first (4-8 weeks), then DX + insurance,
   full platform by September.

## Chosen Approach: Centralized Analytics Layer with Per-Entity Staging

Each entity maintains ownership of their source data and continues using their own
systems (Kaonavi, Excel, DIA). This project builds a read-only centralized aggregation
layer in a single Snowflake account, with per-entity staging schemas that reflect
each source's format, and a unified Gold layer for cross-entity queries.

("Federated" in the organizational sense — source ownership stays distributed — not
in the query-federation/distributed-database sense.)

### Architecture (DuckDB local → Snowflake production)

```
DATA SOURCES
  Kaonavi (API/export)     →  insurance entity master, goals, evals, credentials
  Excel batch (IT entity)  →  ITSS/DSS self-assessments, job history
  DIA (ExaWizards export)  →  DX skill scores (IT + business employees)
  Udemy (API/export)       →  learning activity, course completions, skill tags
  [DX entity source TBD]   →  unknown until audit

BRONZE LAYER — raw ingestion, untouched, per source
  raw_insurance.*    ← Kaonavi exports
  raw_it.*           ← Excel ITSS/DSS files
  raw_dia.*          ← DIA assessment results
  raw_udemy.*        ← Udemy activity logs
  raw_dx.*           ← DX entity source (TBD)

SILVER LAYER — AI-assisted normalization, per entity
  silver_insurance.* ← structured employee, goal, eval, credential records
  silver_it.*        ← parsed skill assessments, job history (multi-line cells
                        split, malformed entries corrected via LLM)
  silver_dia.*       ← normalized DX skill scores mapped to skill taxonomy
  silver_udemy.*     ← course completions linked to skill taxonomy tags
  silver_dx.*        ← TBD

GOLD LAYER — unified analytics views
  gold.employees          ← federated employee list with entity tag
  gold.skill_assessments  ← all assessments across sources, unified schema
  gold.skill_taxonomy     ← master taxonomy: ITSS + DSS + DIA + Udemy mappings
  gold.learning_activity  ← Udemy completions per employee per skill area
                            (conditional on Udemy API access — see Open Questions)
  gold.goals              ← Kaonavi goal records (life insurance, post-May 2026)
  -- gold.career_history: deferred post-September; not required for CIO's
  --   primary use case ("who has skill X")

ANALYTICS
  view: skills_heatmap          — skill × entity × level distribution
  view: talent_map              — employee × skill × level × entity
  -- view: skills_gap_analysis: deferred until gold.goals is populated and
  --   a "required skills per role" source is defined (post-May 2026)
```

### Core Gold Table: skill_assessments

```
gold.skill_assessments
  assessment_id       PK
  global_employee_id  FK → gold.employees.global_id
  canonical_skill_id  FK → canonical_skills.id
  assessment_date     DATE         -- date of the Excel submission / DIA cycle
  file_vintage        VARCHAR      -- source file identifier (e.g. "IT_2025H2.xlsx")
  level_score         INT          -- 1-5, from human entry; never AI-modified
  experience_score    INT          -- 1-5, from human entry; never AI-modified
  source              ENUM(excel_itss, excel_dss, dia, udemy_inferred)
  source_system       VARCHAR      -- kaonavi / excel / dia / udemy
  assessed_by         ENUM(self, manager, external)
  normalization_flag  BOOLEAN      -- true if this row was touched by AI normalization
  normalization_conf  FLOAT        -- LLM confidence score 0-1 for normalized fields
                                   -- NULL if no normalization applied
  needs_review        BOOLEAN      -- true if normalization_conf < 0.8; routed to
                                   -- manual review queue before Gold promotion
```

**Data correction protocol:**
- Bronze records are immutable — raw files preserved as-is.
- Silver records are re-runnable from Bronze at any time.
- Gold views recompute on next pipeline run after Silver is corrected.
- If a CIO-facing report is found to contain a normalization error, correct the
  Silver record, re-run the Gold view, and note the correction date in the
  `file_vintage` field. No silent updates.

### AI Normalization Detail (Bronze → Silver for IT Excel)

The LLM normalization step handles:
- **Multi-line cells**: A single "job history" cell containing multiple roles/projects
  split into one row per record with parsed role, project, start/end dates
- **Single-line multi-record entries**: "4 years cloud infra, 2 years Java dev" →
  two structured rows
- **Typos and inconsistent field names**: Skill category names that drift across
  Excel versions (e.g., "クラウドインフラ" vs "クラウド基盤") normalized to canonical IPA terms
- **What AI does NOT touch**: The explicit 1–5 level and experience scores entered
  by the employee. These pass through unchanged.

### Skill Taxonomy Design

```
skill_taxonomy
  taxonomy_id       PK
  source            ENUM(itss, dss, dia, udemy, internal)
  source_code       VARCHAR   -- original code from that framework
  source_label_ja   VARCHAR   -- original Japanese label
  source_label_en   VARCHAR   -- English label
  canonical_id      FK → canonical_skills.id  -- unified mapping
  itss_job_category VARCHAR   -- ITSS job category if applicable
  itss_specialty    VARCHAR   -- ITSS specialty field if applicable

canonical_skills
  id                PK
  label_ja          VARCHAR
  label_en          VARCHAR
  domain            ENUM(infrastructure, development, data, security,
                         management, dx, business, other)
  ipa_standard      ENUM(itss, dss, none)
```

### Employee Identity (Critical Design Problem)

Each entity uses its own employee numbering. Cross-entity joins require a resolution
strategy:

```
entity_employees
  global_id         PK  -- generated UUID or group-wide ID if one exists
  entity            ENUM(insurance, it_subsidiary, dx_subsidiary)
  local_id          VARCHAR  -- employee number in that entity's system
  source_system     VARCHAR  -- kaonavi / excel / dia / etc.
  name_canonical    VARCHAR  -- normalized name for fuzzy match fallback
  join_date         DATE

-- Resolution: prefer group-wide employee number if available.
-- Fallback: name + entity + join_date matching, flagged for manual review.
-- The audit must determine whether a group-wide ID exists.
--
-- Manual review workflow (fallback only):
--   1. Pipeline outputs an unmatched_employees.csv after each ingestion run.
--   2. Reviewed by author + one HR contact at the relevant entity.
--   3. Confirmed matches are written to a entity_employee_xref override table.
--   4. Cross-entity Gold queries exclude unresolved records (not silently wrong).
--   5. Initial run: expect 2-5% unmatched for a 1,500-person org (~30-75 records).
--      Target: resolve within 1 week of first ingestion run.
```

## Open Questions

1. **Excel audit**: What columns exist in each entity's Excel files? How much
   do they diverge? This is the critical path item — schema Silver layer cannot
   be finalized without it.

2. **Employee identity**: Does a group-wide employee number exist across all
   three entities? If not, what is the reliable cross-entity matching key?
   (Name alone is unsafe for a Japanese org with common surnames.)

3. **DX subsidiary data source**: DIA covers DX skills. What other data exists
   for DX subsidiary employees? Same ITSS/DSS Excel as IT entity? Different?

4. **Kaonavi export mechanism**: API or periodic file export? What cadence?
   Real-time sync is not required, but weekly or monthly export schedule needs
   to be agreed with the life insurance HR division.

5. **DIA export format**: How does ExaWizards deliver DIA results? CSV, API,
   or web dashboard only? If web-only, this is a scraping/manual export problem.

6. **Udemy API access**: Does the company's Udemy license include API access
   for learning activity data? Some Udemy for Business licenses restrict this.

7. **HRMOS historical extraction**: One-time only — if HRMOS is shut down,
   extract historical evaluation records before shutdown as a Bronze archive.
   HRMOS is not an ongoing data source dependency.

8. **IPA skill level mapping**: The Excel uses a 1–5 scale. ITSS defines 7
   proficiency levels. The canonical mapping (e.g., Excel level 3 = ITSS level 4)
   needs to be agreed and documented before any gap analysis is valid.

## 暗号化ポリシー（Encryption Policy）

### 背景

PoCフェーズでは専用ロール・スキーマを持たず、部内の他プロジェクトと共有ロールを使用している。
このため、個人情報を含む列は列レベルで暗号化している。
本番移行時は専用ロール・スキーマによるRBAC制御に切り替える予定。

### 暗号化方式

- Snowflake組み込みの `ENCRYPT()` / `DECRYPT_AS_STRING()` 関数を使用（AES-256-GCM）
- パスフレーズはSnowflake外部で管理し、セッション変数として渡す

セッション開始時に必ず以下を実行すること：

```sql
SET passphrase = '（パスフレーズをここに入力）';
```

### 暗号化対象列

以下の列は `BINARY` 型で格納されており、参照時は必ず復号すること。

| テーブル | 暗号化列名 | 元の型 | 内容 |
|---|---|---|---|
| `entity_employees` | `name_enc` | VARCHAR | 氏名 |
| `employee_reviews` | `score_enc` | INTEGER | 評価スコア（1–5） |
| `employee_reviews` | `comment_enc` | VARCHAR | 評価コメント（自由文） |

### クエリの書き方

**復号して参照する（標準パターン）：**

```sql
SELECT
  emp_id,
  DECRYPT_AS_STRING(name_enc, $passphrase)::VARCHAR    AS name,
  DECRYPT_AS_STRING(score_enc, $passphrase)::INTEGER   AS eval_score,
  DECRYPT_AS_STRING(comment_enc, $passphrase)::VARCHAR AS eval_comment
FROM employee_reviews;
```

**暗号化して保存する：**

```sql
UPDATE employee_reviews
SET
  score_enc   = ENCRYPT(TO_VARCHAR(eval_score), $passphrase),
  comment_enc = ENCRYPT(eval_comment, $passphrase);
```

**集計クエリの例：**

```sql
SELECT
  department,
  AVG(DECRYPT_AS_STRING(score_enc, $passphrase)::INTEGER) AS avg_score
FROM employee_reviews
GROUP BY department;
```

### Cortex Code への指示

このドキュメントを参照してSQLを生成する際は、上記の暗号化列に対して必ず
`DECRYPT_AS_STRING(列名, $passphrase)` を使用すること。
平文の列名（`name`, `eval_score`, `eval_comment`）は存在しない。

### 本番移行時の対応

以下が完了した時点で暗号化を解除し、RBACに切り替える：

1. 専用データベース・スキーマの発行（Snowflake管理者への申請）
2. `ROLE: talent_mgmt_admin` および `ROLE: talent_mgmt_reader` の作成
3. Dynamic Data Masking の適用（評価スコア等）
